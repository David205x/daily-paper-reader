## 摘要
大型语言模型（LLM）日益依赖外部工具来完成复杂的现实世界任务，使得工具文档成为LLM代理的关键基础资源。现有研究主要侧重于提升LLM代理的工具使用能力，而往往将工具文档视为固定输入。尽管近期一些工作尝试通过重写或压缩来优化工具文档，但关于工具文档中包含的信息如何在不同设置中影响代理性能，我们知之甚少。为填补这一空白，我们对LLM代理的工具文档进行了大规模实证研究。研究揭示了现有工具文档在信息字段上存在显著的异质性。此外，不同信息字段的有效性高度依赖于任务领域、LLM主干网络和代理范式，这表明没有任何固定的工具文档能够在多种代理设置中始终如一地泛化。受这些发现启发，我们提出了DocsChisel，一个面向LLM代理的自适应工具文档优化框架。DocsChisel分析目标LLM代理失败的执行轨迹，以识别与文档相关的问题，并通过为每个工具添加、删除和细化信息字段来迭代优化工具文档。我们将DocsChisel与两个最先进的基线方法（即EasyTool和DRAFT）进行了评估。实验结果表明，DocsChisel将LLM代理的任务成功率相对于原始工具文档提升了95.89%，相较于现有基线平均提升了75.15%，同时仅产生有限的优化时间和令牌开销。

## Abstract
Large language models (LLMs) increasingly rely on external tools to accomplish complex real-world tasks, making tool documentation a critical grounding resource for LLM agents. Existing studies mainly focus on improving the tool-use capabilities of LLM agents, while largely treating tool documentation as a fixed input. Although several recent works attempt to optimize tool documentation through rewriting or compression, little is known about how the information contained in tool documentation affects agent performance across different settings.   To bridge this gap, we conduct a large-scale empirical study on tool documentation for LLM agents. Our study reveals substantial heterogeneity in the information fields provided by existing tool documentation. Moreover, the effectiveness of different information fields is highly dependent on the task domain, LLM backbone, and agent paradigm, indicating that no fixed tool documentation can consistently generalize across diverse agent settings.   Motivated by these findings, we propose DocsChisel, an adaptive tool documentation optimization framework for LLM agents. DocsChisel analyzes failed execution traces of a target LLM agent to identify documentation-related issues, and iteratively optimizes tool documentation by adding, removing, and refining information fields for each tool. We evaluate DocsChisel against two state-of-the-art baselines, i.e., EasyTool and DRAFT. Experimental results show that DocsChisel improves the task success rate of LLM agents by 95.89% over the original tool documentation and by 75.15%, on average, over existing baselines, while incurring limited optimization time and token overhead

- **研究动机**：如果不同设置下信息字段的有效性存在显著差异，那么任何固定的文档模板都无法通用，必须发展自适应优化方法。该研究正是为填补这一空白而展开。

## 2. 论文提出的方法论

### 核心思想
DocsChisel 提出"以信息字段（information field）为粒度、以失败轨迹为证据、以迭代反馈为驱动"的自适应工具文档优化框架。其核心主张是：不应将工具文档视为静态输入，而应依据目标代理的实际行为动态增删和细化字段。

### 关键技术细节（四阶段流程）

1. **领域感知执行分析（Domain-Aware Execution Profiling）**
   - 按任务领域组织工具与查询，建立工具与查询的关联。
   - 每个工具的关联查询划分为优化集、验证集（评估集在后续阶段单独划分）。
   - 在原始文档下执行目标代理，记录失败轨迹与成功轨迹，并记录初始验证集成功率作为基线。

2. **记忆引导的文档优化（Memory-Guided Documentation Optimization）**——每轮迭代分解为三个 LLM 辅助步骤：
   - **失败轨迹诊断（Failed Trace Diagnosis）**：结合当前文档、失败轨迹、ground truth 和域级诊断记忆，识别代理失败原因并归因到可能的信息字段，生成"失败证据—行为偏差—相关字段"记录。
   - **字段操作规划（Field Operation Planning）**：基于诊断记录，将问题映射到字段级操作（Add / Remove / Refine），并利用规划记忆合并重复操作、消除冲突，形成统一操作计划。
   - **优化文档生成（Optimized Documentation Generation）**：以原始文档为语义锚点，仅在操作计划指定的字段上进行增删改，避免整体重写导致的信息漂移。

3. **候选评估与反馈更新（Candidate Evaluation and Feedback Update）**
   - 将生成的新文档替换目标工具文档（其余工具保持不变）后，重跑验证集以更新候选集。
   - 回归感知评估：检查优化集上原本成功的查询是否因新文档而失败，收集回归集合；仅在验证集成功率不下降时将该文档纳入候选集。
   - 更新域级记忆（诊断记忆、规划记忆、生成记忆）以指导下一轮迭代，形成闭环。

4. **最终文档选择（Final Documentation Selection）**
   - 达到预设最大迭代次数后，从候选集中选取验证集成功率最高的文档；若有并列，则选择更短的文档以降低上下文开销。

## 3. 实验设计

- **实证研究数据**：收集了 14 个代表性工具使用数据集（WorkBench、API-Bank、ToolLLM、APIBench、ToolAlpaca、AnyToolBench、ToolBench、ShortcutsBench、WildToolBench、SWE-bench、CRMArena、τ-bench、TooLe、ToolLens），共 24,955 个工具及其文档。
- **评估基准**：
  - RQ1（构成分析）：14 个数据集的全部文档。
  - RQ2（影响分析）：WorkBench 的 26 个工具，覆盖 5 个任务领域（数据分析、邮件管理、日历管理、项目管理、CRM）。
  - RQ3–RQ6（方法评估）：WorkBench 与 API-Bank 组合，覆盖 9 个任务领域（新增金融、健康、信息检索、智能家居），74 个工具，2,072 条用户查询；按 5:1:4 划分为优化/验证/测试集。
- **对比方法**：原始文档（OG）、EasyTool（固定模板压缩与标准化）、DRAFT（基于工具执行反馈的迭代优化）。
- **评估指标**：任务成功率（TS，任务是否最终完成）与工具调用正确性（TC，预测工具集合是否与 ground truth 完全一致）。
- **变量设置**：3 种 LLM 主干（GPT-4o、GLM-5、Claude Haiku 4.5）×2 种代理范式（ReAct/LangChain、Multi-Agent/AutoGen）。

## 6. 论文的主要结论与发现

- **实证发现**：现有工具文档存在显著的跨数据集构成异质性——17 种信息字段中，仅工具名和功能描述在所有数据集中出现，使用指导和调用约束仅存于 2 个数据集；同一字段在不同任务领域、LLM 主干和代理范式下的效果可能相反（如在 GPT-4o 下删除"参数可选标志"降低成功率，在 Claude Haiku 4.5 下反而提升 7.5 pp）。
- **核心主张**：固定的文档模板无法在不同代理设置中泛化，必须基于执行反馈自适应优化。
- **方法效果**：
  - DocsChisel 相较原始文档平均提升 TC 达 34.69%、TS 达 95.89%；
  - 与最强基线比较平均提升 TC 26.23%、TS 46.11%；

## 7. 优点

- **填补研究空白**：首次系统性地从信息字段粒度研究工具文档对 LLM 代理效果的影响，揭示"文档—代理"交互的复杂性，为后续研究建立分析框架和字段分类学。
- **方法创新性**：将文档优化从"整体改写/压缩"提升到"字段级自适应增删改"，结合失败轨迹诊断和三类记忆（诊断/规划/生成记忆）跨工具迁移经验，设计新颖且具有工程可行性。
- **实验严谨性较好**：多变量控制、重复运行与统计检验相结合，兼顾 TC 与 TS 两种粒度指标，并关注回归风险；域级组织方式与工具关联查询的划分策略考虑了多工具协作场景，设计细致。
- **实用性**：优化后的文档长度仅比原始增长 24.02%，与 DRAFT 相当，且优化 token 消耗低于 DRAFT，上下文开销可控，具备部署潜力。

## 8. 不足与局限

- **外部效度有限**：评估仅基于 WorkBench 和 API-Bank 两个基准，未覆盖其在实证阶段收集的其余 12 个数据集；9 个领域的代表性和规模有限，跨场景泛化性仍需验证。
- **指标口径单一**：TC 要求工具集合精确匹配，对"部分正确"调用不敏感；TS 可能遗漏部分成功完成但用时过长或路径不优的任务。
- **优化成本与选型依赖**：平均每工具 12.65 分钟的优化耗时显著高于基线；优化模型的选择对结果影响巨大（Claude Haiku 4.5 比 GPT-4o 的 TS 高出 164.71%），这说明方法本身仍高度依赖 LLM 的诊断与生成能力。
- **主观偏差风险**：信息字段识别和文档变体的构建依赖人工标注；虽通过多人独立分析与一致性检验（κ = 0.862），仍可能存在标注偏差。
- **LLM 随机性**：LLM 推理的固有随机性无法完全消除；虽然通过多次重复实验缓解，但各次实验规模有限，极端情况可能被低估。
- **文档优化边界**：该方法无法修复非文档来源的失败（如任务分解错误、用户查询不完整等），存在性能改进天花板。
